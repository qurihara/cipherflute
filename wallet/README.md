# 暗号笛ウォレット（段階0）

笛を吹くと、その場で秘密鍵が組み立てられ、Polygon Amoy 上の口座が現れる。鍵はどこにも保存しない。
契約は使わない（段階0）。設計の検討は [DESIGN.md](DESIGN.md) にある。

## 中身

| ファイル | 役割 |
|---|---|
| `index.html` | 画面。笛を吹く→鍵を作る→アドレスと残高を出す→送る |
| `flute_key.js` | 秘密から口座を作る。PBKDF2（60万回）→ secp256k1 → keccak |
| `flute_key.test.js` | 鍵導出の検査。`node docs/dapp/flute_key.test.js`（9件） |
| `tx.js` | 取引を組み立てて署名する。RLP・EIP-1559・secp256k1 |
| `tx.test.js` | 送金の検査。`node docs/dapp/tx.test.js`（29件） |
| `vendor/` | 外部ライブラリの実体。CDNから読まず、ここに置いたものだけを使う |

## 鍵の作り方（仕様）

```
入力 = 秘密のバイト列                        （合言葉が空のとき）
入力 = 秘密のバイト列 ‖ 0x1f ‖ 合言葉         （合言葉があるとき）
salt = "cipherflute/v1" + "|" + ラベル        （例 "cipherflute/v1|amoy"）
seed = PBKDF2-HMAC-SHA256(入力, salt, 600000回, 32バイト)
秘密鍵 = seed（曲線の外に出たら salt に通し番号を足して作り直す）
アドレス = keccak256(公開鍵の非圧縮65バイトの先頭1バイトを除いた部分) の下位20バイト
```

[* 合言葉は秘密の側に混ぜる]（saltではなく）。saltは公開してよいものとして扱っており、
合言葉は秘密の一部だからである。区切りに 0x1f を入れるのは境目を曖昧にしないためで、
これが無いと 秘密"26"＋合言葉"0812" と 秘密"260"＋合言葉"812" が同じ入力になってしまう。
[* 合言葉が空のときは何も足さない]ので、これまでに作った口座は変わらない。

[* この仕様を変えると、既に印刷した笛が別の口座を指す]。版（`cipherflute/v1`）と繰り返し回数は
仕様の一部であり、迂闊に変えてはいけない。検査（`flute_key.test.js`）がその見張りである。

## 手元で動かす

```
python3 -m http.server 8765 --directory docs
```
のあと `http://localhost:8765/dapp/` を開く。ES モジュールを使うので `file://` では動かない。

## 送金の作り

`tx.js` が担う。EIP-1559（type 2）の取引を組み立て、RLPで符号化し、keccak256でハッシュし、
笛から導いた鍵で署名して `eth_sendRawTransaction` で送る。財布アプリは介さない。

[* 押しただけでは送らない。] 先に「内容を確かめる」で、送り主・宛先・金額・手数料の上限・
合わせて要る額・通し番号・チェーンを画面に出す。人が読んでから署名する。

検査は `node docs/dapp/tx.test.js`（29件）。RLPを公式の例で照合し、[* 署名から署名者の
アドレスが復元できること]を確かめている。ここが1バイト狂うと、署名は通るのにチェーンが
受け取らない、あるいは別の内容の取引として通ってしまう。

手数料は、そのときの基準手数料が2倍に上がっても通る上限を取る。使われなかった分は返る。
Amoyは優先手数料に最低25 gwei前後を要求するので、下限を置いてある。

## ★これは実験である★

[* 本物の資産には使わない。] カード1枚の秘密は20.8bitしかないので、そこから導いた口座の
アドレスが公開の台帳に載った瞬間、[* 総当たりで秘密鍵に到達される]。テストネットのトークンには
金銭価値が無いので損害は出ないが、同じ作りを本番のチェーンで使ってはならない。
価値のあるものを預けるなら、128bitの秘密（スプール2枚）を使うか、笛の秘密と利用者が覚えている
合言葉を混ぜて2要素にする。詳しくは [DESIGN.md](DESIGN.md) の2.2を読むこと。
